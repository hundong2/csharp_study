# 초보자 이해도 체크 — 정답을 보기 전에 말로 답하기

각 질문에 한두 문장으로 답한 뒤 아래 정답 예시와 비교하세요. 문장을 외우기보다 코드의 어느 줄이 근거인지 찾는 것이 목표입니다.

## 질문

1. cache hit와 cache miss는 각각 무엇인가요?
2. TTL이 5분일 때 원본 확인 후 정확히 5분이 지난 값은 왜 만료인가요?
3. `ProductSku`를 그냥 `string`으로 두지 않은 이유는 무엇인가요?
4. `record`가 여러 Task가 공유하는 가격과 캐시 항목에 잘 맞는 이유는 무엇인가요?
5. `PriceQueryService`가 `CachedPriceProvider` 구체 형식을 직접 알지 않는 이유는 무엇인가요?
6. `ConcurrentDictionary`를 썼는데도 `SemaphoreSlim`이 필요한 이유는 무엇인가요?
7. gate를 얻은 뒤 캐시를 다시 확인해야 하는 이유는 무엇인가요?
8. `await gate.WaitAsync(token)`이 `try` 블록보다 앞에 있는 이유는 무엇인가요?
9. `finally`에서 `Release()`하는 이유는 무엇인가요?
10. `TimeProvider`를 주입하면 테스트가 어떻게 좋아지나요?
11. 미발견은 `Result<T>`인데 취소는 예외로 전파하는 이유는 무엇인가요?
12. 실패 Result를 캐시하지 않을 때 동시 대기자에게 어떤 일이 생길 수 있나요?
13. SKU별 `SemaphoreSlim`은 전체 Repository 호출량을 제한하나요?
14. TTL이 지난 항목은 자동으로 메모리에서 제거되나요?
15. 같은 애플리케이션을 서버 두 대에서 실행하면 이 gate가 두 서버를 함께 조정하나요?

## 손으로 추적하기

다음 상황의 Repository 호출 횟수와 각 요청 출처를 적으세요.

```text
00:00 A: LAPTOP-15 요청
00:01 B: LAPTOP-15 요청
00:04:59 C: LAPTOP-15 요청
00:05:00 D: LAPTOP-15 요청
```

조건: TTL은 5분이고 첫 원본 조회와 저장은 00:00에 즉시 성공합니다.

## 정답 예시

<details>
<summary>답을 작성한 뒤 펼치세요</summary>

1. hit는 신선한 캐시 값을 재사용하는 경우이고, miss는 값이 없거나 만료되어 원본 조회가 필요한 경우입니다.
2. 정책이 `age < Lifetime`을 사용하므로 정확히 5분인 순간에는 조건이 거짓입니다. 경계를 명확히 정해야 서버마다 다른 해석을 피할 수 있습니다.
3. `ProductSku.Create` 한곳이 정규화와 검증을 보장합니다. 이후 계층은 이미 유효한 코드라고 믿을 수 있고 값 동등성으로 캐시 키도 일관됩니다.
4. 불변 record는 생성 뒤 내부 값이 바뀌지 않고 값으로 비교됩니다. 공유 중 상태가 몰래 변할 가능성을 줄여 동시성 추론이 쉬워집니다.
5. `IPriceProvider`에 의존하면 Application Service를 고치지 않고 캐시 구현이나 가짜 구현을 교체할 수 있습니다. DIP와 테스트 용이성을 위한 선택입니다.
6. 사전의 개별 연산은 안전해도 `확인 → 원본 조회 → 저장`이라는 여러 단계 전체는 원자적이지 않습니다. 여러 요청이 같은 miss를 보고 동시에 원본을 읽을 수 있습니다.
7. 기다리는 동안 leader가 캐시를 채웠을 수 있습니다. 재확인하지 않으면 차례를 받은 모든 follower가 다시 원본을 호출합니다.
8. `WaitAsync`가 취소되면 gate를 획득하지 못했습니다. 그 상태에서 `finally`가 실행되어 `Release`하면 semaphore count가 잘못 증가할 수 있으므로 획득 뒤에만 `try/finally`를 시작합니다.
9. 성공 반환, 실패 반환, 취소, 예상 밖 예외 어느 경로에서도 획득한 gate를 풀어 후속 요청의 영구 대기를 막습니다.
10. 실제 5분을 기다리지 않고 수동 시계를 이동해 TTL 직전과 정확한 경계를 빠르고 반복 가능하게 검증합니다.
11. 미발견은 정상 업무에서 예상하고 처리할 결과입니다. 취소는 호출자가 작업 중단을 요청한 제어 흐름이므로 일반 실패값과 구분해 전파합니다.
12. leader 실패 뒤 cache hit가 없으므로 대기자들이 gate를 차례로 얻어 원본을 다시 시도할 수 있습니다. 이 구현은 성공 refresh를 합치지만 모든 실패 결과를 공유하지는 않습니다.
13. 아닙니다. 같은 SKU만 직렬화하고 다른 SKU는 병렬로 진행합니다. 전체 제한에는 별도의 semaphore나 rate limiter가 필요합니다.
14. 아닙니다. 다시 조회할 때 신선하지 않다고 판단할 뿐 백그라운드 eviction을 하지 않습니다.
15. 아닙니다. `ConcurrentDictionary`와 `SemaphoreSlim`은 한 프로세스 메모리 안에서만 공유됩니다. 다중 서버에는 분산 캐시나 별도 조정이 필요합니다.

손 추적 답: A는 원본, B와 C는 캐시, D는 정확한 만료 경계이므로 원본입니다. Repository 호출은 총 2회입니다.

## 최종 자기 설명

아래 빈칸을 채우고 소리 내어 읽어 보세요.

> `ConcurrentDictionary`만으로는 **확인 → 원본 조회 → 저장** 전체가 원자적이지 않아서, 이 예제는 **SKU**별 `SemaphoreSlim`을 쓰고 gate 안에서 **캐시 freshness**를 다시 확인한다.

이 문장을 코드 없이 설명할 수 있고 자체 테스트 `7/7`을 통과했다면 오늘의 핵심을 이해한 것입니다.
