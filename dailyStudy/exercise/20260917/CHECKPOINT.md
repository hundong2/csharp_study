# 2026-09-17 이해도 확인

코드를 가리고 먼저 답해 보세요. 답을 확인한 뒤 틀린 이유를 [`README.md`](./README.md)의 해당 절이나 C# 주석에서 다시 찾습니다.

1. 커서가 `(10:00, 1)`이고 `(10:00, 2)` 주문이 있다면 다음 페이지에 포함되나요?
2. `CreatedAtUtc`만으로 정렬하거나 커서를 만들면 어떤 문제가 생기나요?
3. `PageSize + 1`건을 읽는 이유와 사용자에게 실제 반환하는 건수는 무엇인가요?
4. `After = null`과 `NextCursor = null`은 각각 무엇을 뜻하나요?
5. `PageSize = 0`은 Result, 저장소 장애는 예외, 호출자 취소는 별도 취소로 처리하는 이유는 무엇인가요?
6. `IOrderRepository`를 Service가 사용하고 `Program`이 구체 구현을 연결하는 구조가 테스트에 주는 이점은 무엇인가요?
7. 필터를 건 뒤 페이지를 자르는 것과 페이지를 자른 뒤 필터를 거는 것은 왜 다른가요?
8. 이 예제가 여러 페이지에 걸친 동일한 DB 스냅샷을 보장하나요?

## 정답과 설명

1. **포함됩니다.** 시각이 같아도 ID가 1보다 크기 때문입니다.
2. **중복 시각의 행을 건너뛰거나 순서가 불안정해질 수 있습니다.** 시각과 고유 ID를 함께 정렬하고 같은 두 값을 커서로 사용합니다.
3. **다음 페이지의 존재를 판정하려는 것입니다.** 최대 `PageSize`건만 사용자에게 돌려줍니다.
4. 요청의 `After = null`은 처음부터 조회, 응답의 `NextCursor = null`은 현재 조건에서 다음 페이지가 없음을 뜻합니다.
5. 잘못된 크기는 사용자가 수정할 수 있는 예상 오류이고, 저장소 장애는 운영 진단과 재시도가 필요한 기술 실패입니다. 취소는 호출자의 중단 요청이므로 일반 오류로 바꾸지 않고 전파합니다.
6. Service를 메모리 저장소 없이도 테스트 대역으로 검증할 수 있습니다. `Program`은 실제 실행에서 쓸 구현을 한곳에서 조립합니다.
7. 먼저 자르면 잘린 구간에 원하는 상태가 적을 때 페이지가 일찍 비거나 원하는 주문을 건너뛸 수 있습니다. 예제는 생성자에서 한 번 정렬하고, 조회할 때 필터를 제한보다 먼저 적용합니다.
8. **아니요.** 메모리의 고정 목록에서 경계 계산을 학습합니다. 동시 추가·삭제까지 동일 시점으로 묶으려면 별도 저장소 일관성 설계가 필요합니다.
