# 2026-09-17 실행 연습문제 — 커서 기반 주문 조회

먼저 [README의 읽는 순서](./README.md#코드-읽는-순서-reading-order)를 따라 데모와 자체 검증을 실행하세요. 각 과제는 코드를 바꾸기 전에 입력과 예상 결과를 한 줄로 적고 시작합니다.

## Beginner — 정렬 키 손으로 따라가기

1. `CreatedAtUtc`가 같은 주문 세 건과 다음 시각의 주문 한 건을 적고, `(CreatedAtUtc, Id)` 오름차순으로 정렬합니다.
2. 페이지 크기를 2로 두고 첫 페이지, 다음 커서, 둘째 페이지를 손으로 써 봅니다.
3. `Infrastructure.cs`의 비교 조건과 자신의 결과를 대조합니다. `Id` 비교를 제거하면 어느 주문이 빠지는지도 적습니다.

**완료 기준:** 두 페이지를 합쳤을 때 네 ID가 정확히 한 번씩 나타나야 합니다.

## Intermediate — 입력 검증 강화

`OrderSearchService`가 허용하는 페이지 크기 상한을 바꾸어 보고, 0·상한·상한+1을 각각 조회하세요. `--self-test`의 경계 검증도 새 상한에 맞게 고칩니다. 예상 가능한 잘못된 요청은 Result로 돌아오고 프로그램 오류는 숨기지 않아야 합니다.

**완료 기준:** 유효한 경계는 성공하고 양쪽의 잘못된 값은 명확한 오류 결과를 줍니다.

## Advanced — 필터를 유지한 채 다음 페이지 조회

특정 상태의 주문만 선택하여 페이지 크기 1로 끝까지 읽으세요. 필터링을 `Take`보다 **앞**에 두어야 하는 이유를 예시 세 건으로 설명합니다. 결과에 선택하지 않은 상태가 없고, 같은 상태의 주문이 빠지지 않는 자체 검증을 추가합니다.

**완료 기준:** 이어지는 모든 요청에서 같은 필터를 사용하며, 결과 ID에 중복이 없습니다.

## Pro — 운영 저장소 설계 검토

코드를 바로 늘리기보다 다음 네 질문의 답을 짧은 설계 메모로 작성하세요.

1. SQL 저장소라면 어떤 복합 인덱스를 만들고 왜 그 순서로 두겠습니까?
2. API에서 커서를 문자열로 노출할 때 클라이언트가 내용을 바꾸지 못하도록 무엇을 확인하겠습니까?
3. 첫 페이지와 둘째 페이지 사이에 주문이 추가되면 어떤 일관성을 약속할 수 있습니까?
4. 이미 사용한 커서를 다른 상태 필터에 다시 쓰면 어떤 혼란이 생기며 어떻게 막겠습니까?

**완료 기준:** 성능, 커서 무결성, 동시 변경, 필터 결합을 각각 별도 문장으로 설명합니다. 운영용 DB 구현은 이 학습 예제 범위 밖입니다.
