## Beginner — 문법과 HTTP 응답 익히기

1. `GET /books`를 호출하기 전과 책 한 권을 `POST /books`로 추가한 뒤의 JSON을 비교하세요. 배열 `[]`와 객체 `{}`가 각각 무엇을 나타내는지 적어 보세요.
2. 제목을 빈 문자열로 보낼 때 상태 코드와 오류 본문을 확인하세요. [`BookService.cs`](./src/ReadingListApi/Application/BookService.cs)에서 그 조건을 찾고, [`BookEndpoints.cs`](./src/ReadingListApi/Api/BookEndpoints.cs)가 이를 HTTP로 어떻게 바꾸는지 추적하세요.
3. `GET /books?status=toRead`와 `GET /books?status=completed`의 결과를 비교하세요. 새 책의 기본 상태와 필터가 적용되는 위치를 설명해 보세요.

## Intermediate — 작은 기능 추가하기

1. 현재 제목·저자 제한은 각각 `string.Length <= 100`입니다. 저자만 50 이하로 바꿔 보세요. 서비스에서 예상 가능한 실패로 반환하고, 자체 검증에 길이 50 성공과 51 실패를 추가하세요. 공백만 있는 저자도 계속 거절해야 합니다.
2. `GET /books`에 `author` 쿼리 매개변수를 추가해 저자 이름으로 좁혀 보세요. 빈 저자 필터가 전체 조회인지 오류인지 계약을 먼저 결정하고 README에 적으세요.
3. 잘못된 `status` 쿼리의 400과 없는 ID의 404에서 `status`, `title`, `detail`을 비교하세요. 빈 제목의 400은 `errors.book`을 확인하세요. 오류가 발생한 위치와 HTTP 변환을 한 문장씩 설명하세요.

## Pro — 운영 경계 생각하기

1. 저장소를 파일 또는 DB로 교체한다고 가정하고 `IBookRepository` 계약에서 유지할 것과 바꿀 것을 적어 보세요. 재시작 후 데이터 보존, 동시 요청, 테스트 대역을 각각 어떻게 확인할지 계획하세요.
2. `POST /books`의 재시도 때문에 같은 책이 두 번 추가되지 않도록 하려면 무엇이 필요한지 설계해 보세요. 요청 식별자 헤더와 멱등성 키의 차이도 설명하세요.
3. 예외 처리 미들웨어의 위치를 바꾼 뒤 어떤 예외를 잡을 수 있는지 실험해 보세요. 학습용 실험 뒤에는 원래 순서로 되돌리고 검증을 다시 실행하세요.

## 완료 기준

- `dotnet build`가 성공합니다.
- `--self-test`가 모두 통과합니다.
- 직접 보낸 정상 요청과 잘못된 요청에서 예상 상태 코드 및 본문을 확인했습니다.
- 변경한 규칙의 이유와 테스트 방법을 다른 초보자에게 설명할 수 있습니다.
