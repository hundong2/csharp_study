# 2026-09-18 이해도 확인 — HTTP 요청에서 서비스까지

[학습 안내로 돌아가기](./README.md)

먼저 아래 질문에 **코드를 보지 않고** 답하세요. 헷갈리면 [구조도](./README.md#의존성-구조도)와 해당 소스의 한글 주석을 다시 읽은 뒤 아래 정답을 펼쳐 보세요.

1. `POST /books`가 성공하면 왜 `200`보다 `201`이 알맞을까요? `Location`은 무엇을 가리키나요?
2. URL의 `/books/{id}`와 `?status=toRead`는 각각 어떤 입력을 전달하나요?
3. 제목이 비어 있는 요청과 저장소의 예상치 못한 장애를 왜 같은 오류로 처리하면 곤란할까요?
4. 요청이 서비스에 도달하기 전에 어떤 구성요소를 지나나요? 응답은 어느 방향으로 돌아오나요?
5. `BookService`가 메모리 저장소 클래스를 직접 만들지 않고 `IBookRepository`를 받는 이유는 무엇인가요?
6. `record`와 `?`는 각각 어떤 뜻이고 이 예제의 어떤 문제를 풀어 주나요?
7. 메모리 저장소를 실제 DB로 바꾼다면 동기 메서드를 비동기로 바꾸는 이유와 요청 취소를 전달할 이유는 무엇인가요?
8. 잘못된 상태 필터와 없는 책 ID는 각각 어떤 HTTP 상태 코드가 알맞을까요?
9. 서버를 재시작한 후 추가한 책이 사라진다면 현재 어댑터의 어떤 성질 때문인가요?
10. `X-Request-Id`가 붙어 있어도 인증과 권한 확인이 필요한 이유는 무엇인가요?

<details>
<summary>정답과 이유 펼치기</summary>

1. 새로운 자원을 만들었으므로 `201 Created`가 의미를 정확히 전합니다. `Location`은 생성된 책을 조회할 수 있는 URL을 가리킵니다.
2. `{id}`는 경로의 책 식별자이고, `status`는 목록을 좁히는 쿼리 값입니다.
3. 빈 제목은 호출자가 고칠 수 있는 예상 가능한 입력 오류라 400으로 설명합니다. 저장소 장애는 서버 오류이며 입력을 바꿔도 해결되지 않을 수 있습니다.
4. 요청은 등록된 순서대로 미들웨어를 지나 엔드포인트와 서비스로 갑니다. 응답은 미들웨어를 역순으로 지나갑니다.
5. 저장소 계약에 의존하면 실제 DB 구현이나 테스트용 구현으로 바꾸기 쉽습니다. 구체 객체를 연결하는 곳은 Composition Root입니다.
6. `record`는 값 중심 자료를 정의하고, `?`는 값이 없을 수 있음을 타입에 드러냅니다. 책·결과 표현과 입력 누락·조회 실패 처리에 도움을 줍니다.
7. DB 작업은 오래 걸릴 수 있으므로 비동기로 처리하면 기다리는 동안 스레드를 계속 붙잡지 않습니다. 클라이언트가 연결을 끊으면 `CancellationToken`을 서비스와 저장소까지 전달해 불필요한 작업을 줄일 수 있습니다. 현재 메모리 예제의 저장소 메서드는 동기식입니다.
8. 잘못된 필터는 `400 Bad Request`, 없는 책은 `404 Not Found`가 알맞습니다.
9. 프로세스 메모리만 사용해 영구 저장을 하지 않기 때문입니다. 운영용이라면 저장소 어댑터를 교체해야 합니다.
10. 요청 식별자는 추적을 돕는 값일 뿐 호출자가 누구인지 증명하거나 자원 접근을 허가하지 않습니다.

</details>
